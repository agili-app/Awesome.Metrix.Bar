# Awesome.Metrix.Bar — Agent Guide

## Project scope

- English is the default language for the site and the primary language for project communication, comments, and documentation. Keep `README.md` and `README.zh-CN.md` concise and in sync, with a short dashboard list linking to the catalog for setup details. Preserve upstream metadata and setup notes in their original language.
- This is a community registry for [Metrix.Bar](https://metrix.bar/), built with [Void](https://void.cloud/), [Vite+](https://viteplus.dev/), and Cloudflare Workers. The public index stays at `https://awesome.metrix.bar/dashboards/index.json`.
- Bind the custom domain manually in Cloudflare. Do not declare `routes`; keep `workers_dev: false` and `preview_urls: false` in `void.config.ts`.
- Serve the registry, `.bar` files, and remote icons through this service. Dashboard scripts retain their original runtime API/CDN connections. Usage, inclusion, and deployment instructions live in the two READMEs.

## Commands and configuration

- Use Node.js 24 and pnpm 12; exact versions are in `.node-version` and `package.json#packageManager`. Void requires Node.js 24.22.0 or newer within the supported Node 24 line. Install with `vp install --frozen-lockfile`.
- Use `^` ranges for direct dependencies, keep the Vite/Vitest aliases and overrides in `package.json` and `pnpm-workspace.yaml` aligned, and keep `@types/node` on Node 24. Commit the lockfile for reproducible installs.
- Vite+, lint, format, and test settings live in `vite.config.ts`. Import `defineConfig` from `vite-plus` and test APIs from `vite-plus/test`; keep `lint.options.typeAware` and `typeCheck` enabled.
- Void and Cloudflare settings live in `void.config.ts`. React pages live in `src/pages/`; server API routes live in `src/routes/` and import handlers from `void/handler`. Keep reusable React components and CSS in `src/views/`.
- Before using ui-sdk, follow the `ui-sdk` skill if installed and read `node_modules/@ui-sdk/react/docs/llms.txt`. To build a new component, also search `node_modules/@ui-sdk/react/docs/core.md` by heading and read `node_modules/@ui-sdk/react/docs/rendering.md`.
- Use `voidReact()` from `@void/react/plugin` alongside `voidPlugin()`; it includes the React Vite plugin. `output: "static"` prerenders the homepage and dashboard detail pages. Detail URLs are `/dashboards/<id>`; `src/pages/dashboards/[id].server.ts#getPrerenderPaths()` must enumerate every published dashboard. Keep complete page content available without browser JavaScript.
- Predictive navigation uses the standalone `js.foresight` entry in `src/client/prefetch.ts`, built through the Vite client input and resolved from its manifest in page middleware. Keep browser DOM types isolated in `src/client/tsconfig.json`. Mark native page links with `data-prefetch`; prefetch at most three distinct same-origin page documents, registering language links only while their menu is open. Preserve normal navigation and complete static content.
- `patches/js.foresight@4.2.1.patch` fixes the dependency's connection order so keyboard prediction resumes after all active links become idle. Keep this patch until an upstream release passes the idle → reopen language menu → keyboard prediction regression check; do not keep the library active with placeholder elements.
- Use Paraglide JS with the Vite plugin in `vite.config.ts`, project settings in `project.inlang/`, and complete translation catalogs in `messages/<locale>.json`. Pass locales explicitly to message functions and child components; only page entry components default to English. Keep localized path helpers in `src/i18n.ts` and metadata in `src/seo.ts`. Do not mutate a global locale during concurrent rendering. English URLs stay unprefixed; other public pages use `/<locale>` and `/<locale>/dashboards/<id>`. Enumerate all supported locales in prerender paths, canonical and alternate links, and the sitemap. Keep registry, icon, avatar, and download URLs unprefixed.
- `patches/@ui-sdk__core@0.1.0-beta.1.patch` lets UI SDK WebMCP activate `Button` roots rendered as native `a[href]` links. Keep native link semantics; remove the patch only after an upstream version passes the WebMCP Add registry, Install, and Download regression test.
- Use Panda CSS with tokens and recipes in `panda.config.ts`, the `@pandacss/vite` plugin before the framework plugins in `vite.config.ts`, and layer declarations in `src/views/site.css`. Follow the installed `panda-css` and `panda-css-theming` skills before styling; use statically extractable `css()` calls and recipes from the generated `styled-system/`, and read its generated token types before choosing tokens. Use ui-sdk `Button` for actions, preserving native anchor semantics for install and download links.
- Page-specific canonical URLs, social metadata, and escaped JSON-LD live in `src/seo.ts`; `/sitemap.xml` lists only public pages. JSON-LD is data, not a hydrated island.
- Author avatars use `https://unavatar.webp.se/github/<username>` through WebP.se, with GitHub usernames listed in `src/authors.ts`. `scripts/build-avatars.ts` preserves successful, nonempty avatar responses without image format validation in Node during registry generation, with a one-day local cache, into ignored `public/avatars/`. Keep existing avatars if a refresh fails; a cold cache still requires a successful download. Serve those files locally with a one-day shared cache. Dashboard files and declared dashboard icons remain hash-pinned.
- Generate the registry with `vp run registry:build` and Void types, Panda helpers, and Paraglide messages with `vp run types`. Run both before standalone checks or tests after a fresh checkout: server modules and tests import `.generated/manifest.json`. Installation runs `vp run types` automatically but does not build the registry; keep `void prepare` first because Panda requires `.void/tsconfig.json`. Use `vp run styles` after changing Panda configuration and `vp run messages:build` to compile translations independently.
- Develop with `vp run dev` at `http://localhost:5173`, build with `vp run build`, and build/preview with `vp run preview`. Built-in `vp dev` and `vp build` skip registry generation; use them only when generated inputs are current.
- Check everything with `vp check`; lint with `vp lint`; check formatting with `vp fmt --check`; check types only with `vp check --no-fmt --no-lint`.
- Run all tests with `vp test`, one file with `vp test tests/worker.test.ts`, one case with `vp test tests/worker.test.ts -t 'exact upstream bytes'`, or watch with `vp test watch`.
- Run full verification with `vp run verify`. With a local server running, use `vp run verify:http -- http://localhost:5173 --dev`. Use `--dev` only for Vite development servers; production verification permits only the local fingerprinted prefetch module and verifies its static and dynamic imports against the Vite manifest; other executable browser scripts are rejected. CI reuses the verified build for the prebuilt deployment dry run and production HTTP checks, then starts `vp dev` for development checks.
- Preview deployment with `vp run deploy:dry-run`; deploy with `vp run deploy`; verify a deployment with `vp run verify:http -- https://awesome.metrix.bar --edge-cache`.
- Void emits Cloudflare Build Output into `.cloudflare/output/v0/`. Deployment scripts use `cf deploy --prebuilt --mode production`, including dry runs. Do not use Wrangler for this output: its dry run can pass while a real deployment aborts. Sign in with `vp exec cf auth login`; cf uses its own credentials.
- `.cache/`, `.generated/`, `styled-system/`, `src/paraglide/`, `public/avatars/`, `.void/`, `.void-wrangler.jsonc`, `.cloudflare/`, `dist/`, and `.wrangler/` are generated and ignored. Do not edit or commit them; commit `pnpm-lock.yaml`. Official tools refresh on each build; cached dashboard and icon downloads are hash-checked on every use.

## Dashboard inclusion

- Treat `registry/sources.json` as the source of dashboard repositories, paths, authors, licenses, and release pins. Check each upstream's actual index and `.bar` metadata when adding or updating dashboards. Preserve source links separately from an application's `homepage`; use `UNLICENSED` if no upstream license is declared.
- Do not execute upstream collectors during registry generation. Dashboard scripts retain their original runtime API/CDN connections; a successful registry build does not validate those connections or a required local collector.
- `registry/sources.json` pins full commits, actual metadata versions, and original-byte SHA-256 hashes. `source.path` tracks the current upstream file; use `release.path` to retain historical locations. Append releases from oldest to newest; retain history so old download URLs keep working. Compare against a Git baseline with `vp run registry:history -- origin/master` (or the actual PR base revision); CI checks pull requests and default-branch pushes. Preserve registry origin and retained dashboards' release bytes, effective upstream paths, and icon pins. Download the official builder and schema without SHA-256 pins; keep dashboard files and remote icons hash-pinned.

## Registry and proxy constraints

- Follow the [official registry protocol](https://metrix.bar/docs/registries.md) and [JSON Schema](https://metrix.bar/dashboards/schema.json), not a custom index format.
- Website app links use `metrixbar://registry/add?url=…` and `metrixbar://install/<id>?registry_url=…`; encode nested URLs as query values. Registry-aware installation preserves updates. Render descriptions and plain-text setup docs from registry metadata; keep download links available.
- IDs match `^[a-z0-9]+(?:-[a-z0-9]+)*$`; dashboard IDs are unique within the registry. `--` is reserved for client installation IDs. Keep published IDs and the index URL stable.
- Versions are strict SemVer and must increase when bytes change. Clients reject a changed hash at the same version; do not overwrite releases.
- `file` is a same-origin `.bar` path resolved relative to the index URL: no leading slash, scheme, host, query, fragment, or backslash. Percent-decoded paths must remain valid.
- Public files resolve under `https://awesome.metrix.bar/dashboards/`. Return their bytes directly; never redirect downloads to GitHub/raw/CDNs. Workers `fetch` requires `redirect: "manual"` with an explicit upstream status 200 check; `redirect: "error"` is unsupported there.
- `sha256` is the 64-character lowercase SHA-256 of the distributed bytes. Preserve encoding and line endings; any byte change requires a new hash, version, and metadata check.
- Do not set `compatibility_date` beyond the installed workerd version. Actually start `vp run dev` when upgrading; unit tests and builds cannot replace this check.
- The proxy accepts only `manifest.assets` mappings, never arbitrary target URLs. Pin remote icon URLs, hashes, and image content types and serve them locally; retain embedded icons.
- Enable Workers Cache and `cross_version_cache` in `void.config.ts`. HTML pages and the index have a 300-second shared cache; hash-addressed resources are immutable for one year; errors use `no-store`. Cache hits reduce execution and upstream traffic but still count as standard Worker requests.

## Required verification

- For documentation-only changes, run `git diff --check` and verify referenced commands, paths, and facts. Report checks that could not run.
- For code or configuration changes, run `vp run verify`. For proxy, route, or dashboard inclusion/update changes, also start the local server and run `vp run verify:http -- http://localhost:5173 --dev`. After deployment, add `--edge-cache` to verify real cache hits.
- To verify production HTTP output after a current build, start `vp preview --host 127.0.0.1 --port 4173 --strictPort`, then run `vp run verify:http -- http://127.0.0.1:4173` without `--dev`. CI also runs `vp exec cf deploy --prebuilt --mode production --dry-run` against the verified build.
- For dashboard additions or updates, verify the official schema, unique IDs, strict SemVer, agreement with `.bar` metadata, and SHA-256 of actual proxy responses. Checking upstream URLs or claimed hashes alone is insufficient.
- For route or proxy changes, verify the homepage, parseable index, relative downloads, no cross-origin redirects, unknown paths, and upstream failures. Error pages must never pass as successful dashboard files.
- The official builder only checks `.bar` files statically. If dashboard content changes, use the Metrix.Bar local API to validate runtime behavior, permissions, and rendering; see the [official guide](https://metrix.bar/docs/registries.md#building-registries-with-buildjs).
